# coach harness — coach.html in REAL mode against a fake Supabase

Built during the coach.html audit (2026-10-10, `docs/record/COACH-AUDIT.md`). It drives `coach.html`
(not `?demo=1`) in headless Chromium with a stubbed `window.supabase`, so the write paths that demo
mode turns into no-ops actually run, and checks both the payload that leaves the page and what the
screen shows afterwards. Every check is written as the CORRECT behaviour: a FAIL is a defect.

All data is MADE UP (`fixtures.js`: ava_test, ben_test, eli_new, cara_free, dan_proof …, addresses at
`example.invalid`). This repo is public: never seed it with real athlete data, and never point it at
the real Supabase project.

**Run it after any change to coach.html's data or write paths** (the editor, saves, loads, auth,
backup, logins, deletes). On 2026-10-10 it went from 32 failing checks to 0.

## Run

```
# 1. serve the repo (any port; COACH_BASE overrides the default)
cd <repo> && python3 -m http.server 8765 --bind 127.0.0.1 &

# 2. the scenarios
node scripts/headless/coach/run.js              # all of them -> $OUT/results.json, backups, screenshots
node scripts/headless/coach/run.js editor backup  # only ids containing one of the words
sh scripts/headless/coach/run-parallel.sh [3]    # the whole suite in 3 parallel shards (SHARD=i/n), one summary: about a third of the time
COACH_BASE=http://127.0.0.1:9000 node scripts/headless/coach/run.js

# 3. (optional) the REAL supabase-js, for the auth events: vendor it once, outside git
cd scripts/headless/coach && mkdir -p vendor-src vendor && cd vendor-src \
  && npm pack @supabase/supabase-js@2.117.3 && tar -xzf supabase-supabase-js-2.117.3.tgz \
  && cp package/dist/umd/supabase.js ../vendor/ \
  && echo '{"supabaseJs":{"package":"@supabase/supabase-js","version":"2.117.3","file":"dist/umd/supabase.js"}}' > ../vendor/VERSION.json
node scripts/headless/coach/reallib.js           # which auth events reach onAuthStateChange, and how many loads
```

`vendor/`, `vendor-src/` are gitignored. Output goes to `$OUT` (default: `<tmp>/coach-harness-out`),
never into the repo. Playwright and Chromium are found where the cloud container keeps them; elsewhere
set `PLAYWRIGHT` (its module path) and `CHROMIUM` (a browser binary). coach.html pins supabase-js
2.117.3; bump the pin and the version here together.

## Knobs (set in a scenario with `page.evaluate(() => …)`)

- `window.__STUB.fail.push({kind:'from'|'rpc'|'fn', name, op?, message, status?, times})` — make the next call(s) fail.
- `window.__STUB.rlsDeny.<table> = ['update','insert','delete']` — the write "succeeds" with zero rows, like PostgREST under RLS.
- `window.__STUB.maxRows` (seed `stub.maxRows`) — PostgREST max-rows cap, default 1000.
- `window.__STUB.missingRpc = ['coach_save_spine']` — those RPCs answer "Could not find the function" (a server that has not had the stage applied).
- `window.__STUB.missingRpc = ['get_courtside']` is also a server that has not had **stage75** applied: all nine Courtside functions answer `PGRST202` and the five tables (`courtside_marks`, `career_honour_months`, `career_honours`, `career_goals`, `career_notes`) answer `PGRST205` ("Could not find the table…"). `window.__STUB.missingTables = ['career_goals']` takes any one table away. `window.__STUB.honoursLive = {sessions: {n, who}, improved: {pct, who: [{athlete_id, lift, pct}]}, full_month: {who, near}, shortlist: […]}` is what the month's honours work out to (seed: `buildSeed({honoursLive})`).
- **`buildSeed({crew: true})` is stage81 (the Bell)**: the stub answers `coach_crew`, `coach_crew_post`, `coach_crew_remove`, `coach_crew_under13` and `crew_photo` from `window.__DB.crew_bell` (`{posts, people, photos, rings_week}`; a post carries `ago_min`, its age in minutes on the page's clock, which the stub turns into `at`, and the stub drops one older than 7 days like `crew_sweep()`). Without `crew: true` those five answer `PGRST202`, so every other scenario runs against a server that has not had stage81 and draws no Bell; `window.__STUB.missingRpc = ['coach_crew']` takes them away from a seeded run too. The stub refuses as the SQL does (`crew:too_long`, then a photo that is not base64 / a JPEG / over 450 KB as `crew:photo_bad` / `crew:photo_big`, then `crew:empty`; `crew:who` for an athlete with no programme). `fixtures.js` `crewSeed()` seeds four posts (Amir's, Ava's, Ben's session, one by an athlete the crew can no longer see) and four answers; a photo is made in the test and put in `__DB.crew_bell.photos[<post id>]` (the harness has no JPEG library). Use `fixedTime: '2026-11-12T10:00:00Z'` so *3h*, *Yesterday*, *Tue* and *Mon* are the same every day.
- **`buildSeed({open: true})` is stage85 (the Monthly Open)**, and turns stage81 on too (the crew is the Bell's yes answers): the stub answers `coach_open`, `coach_open_set`, `coach_open_close`, `coach_open_result` and `coach_open_remove` from `window.__DB.crew_open_state` (`{challenges, results, rings}`), emulated from `supabase/stage85_crew_open.sql` (one live challenge at a time, a new one closes the old, `p_id` corrects the words, one result per athlete, the board's order by `better`, `who` is the athlete id for someone not in the crew, the last five closed, `p_id` only corrects the LIVE one (*no such challenge is open*), a result needs an athlete with a programme (*no athlete "…"*), the Bell line only for a `crew_members()` member with the Open on). Without `open: true` those five answer `PGRST202`, so every other scenario draws no panel; `missingRpc: ['coach_open']` takes them away from a seeded run, `__STUB.openNull = true` makes the read answer nothing, `__STUB.openWriteNull = n` makes the next n writes do their work and answer nothing. `fixtures.js` `openSeed()` seeds two CLOSED challenges (Plank Hold, One Kilometre Row) and no live one, and marks Kim a former athlete; it also gives Kim, the demo and the coach's own identity a programme each, so the result picker's exclusions are real.
- **`buildSeed({lounge: true})` is stage96 (the Players' Lounge, built 2026-10-24, not live)**, and turns stage81 on too (the crew is the Bell's yes answers). The stub answers `coach_crew_faces`, `coach_crew_face_clear`, `coach_cheer`, `coach_crew_cheers`, `coach_cheer_word_clear` and the table `athlete_profile`, in the shapes of `C:\Users\Amir\AA-Lounge\CONTRACT.md`, from `window.__DB.lounge` (`{faces, cheers, seq}`; a face is listed only for a `crew_members()` member (`coach_crew_face_clear` and `coach_cheer_word_clear` answer `{ok:true}`), a cheer is once a day per person on the stub's UTC day, a word is cleaned of quotes, `<`, `>` and backslashes, over 100 letters is `crew:word_long`, a non-member is `crew:gone`) and from the table `athlete_profile`. **`buildSeed({partner: true})` is stage97**: `coach_partner_codes`, `coach_partner_code_make` (answers `{code}`; `partner:has_code`, `partner:under13`, `partner:no_programme`), `coach_partner_credit_add` (`partner:self` for the member's own application, a 23505 for the same application twice), `coach_partner_credit_used`, the table `referral_credits`, two athlete codes (AVA42 with two credits, each with its `intake_id`, and BEN43) and four applications that typed them. Without the option each one answers `PGRST202` (the functions) or `PGRST205` (the tables), which is how every other scenario still runs against an older server; `missingRpc: [name]` takes one away from a seeded run. `fixtures.js` `loungeSeed()` gives Ava a face, makes Jon a Farsi athlete and seeds four cheers (two with a word, one of them markup on purpose); every picture is a one-pixel JPEG.
- `coach_save_spine` is stage64's: it takes `steps` and `suggested_changes`, and refuses what the table's checks refuse (more than 6 steps, a blank one or one over 140 characters, a draft list that is not a list) with the database's code. A server without stage64: `__STUB.fail.push({kind:'rpc', name:'coach_save_spine', message:'exercises.steps cannot be written from the editor'})`.
- `window.__sqlWrite(table, id, patch)` — a write with no signed-in user (Claude's `/spine`, the SQL editor): fires the version trigger as `sql`.
- `window.__STUB.delay.<name> = ms` — extra latency.
- `window.__STUB.afterSelect = (table, call, DB) => {}` — mutate the DB between two reads (concurrency).
- `window.__fireAuth('TOKEN_REFRESHED' | 'SIGNED_IN' | …)` — call every stored onAuthStateChange callback.
- Mutate `window.__DB.<table>` directly to simulate another writer (the pipeline's `publish_cycle`, another tab).
- `openCoach(b, {tz:'Asia/Tehran', fixedTime:'2026-10-09T22:00:00Z'})` — page clock and time zone.
